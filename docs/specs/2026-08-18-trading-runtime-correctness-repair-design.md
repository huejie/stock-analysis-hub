# 交易决策运行与数据正确性修复设计

> 日期：2026-08-18
> 状态：已完成分节确认，等待书面复核
> 适用分支基线：`master`（2026-08-18）

## 1. 背景

线上 `http://106.54.203.187:8888/preview` 的交易决策模块已经具备账户、股池、行情、计划、策略和定时任务等结构，但当前实际运行存在以下阻断：

- 总览将计划列表摘要当作详情使用，访问不存在的 `items`，导致正文空白；
- Scheduler 只返回严格晚于当前时间的任务，随后又要求当前时间达到该未来时间，定时执行分支不可达；
- 股票代码归一化将整个 `0009xx` 前缀视为上交所指数，导致 `000936` 华西股份被映射为 `000936.SH`，并关联到错误的指数行情；
- 数据健康接口与计划生成使用不同的基准集合，页面可显示 `BLOCKED`，计划却可能继续生成；
- 计划生成过程中的 `warnings` 和 `degraded` 没有真实持久化；
- 策略设置页面展示了后端并未消费或实际属于账户的参数；
- 线上热榜已经更新到 2026-08-17，但最新交易股池仍为 2026-08-14 的手工版本，自动同步未形成闭环。

本设计采用分期处理。第一期只恢复运行与数据正确性；第二期另行建设 Hermes 网页任务中心；3～12 个月中长线量化股池是独立后续项目。

## 2. 目标与非目标

### 2.1 目标

1. 总览在计划存在、计划为空和接口失败时都能显示明确状态。
2. Scheduler 能按上海时区执行、补跑、持久互斥、重试并记录结果。
3. 股票与指数代码不再因前缀规则发生资产错配。
4. 数据健康与计划门禁使用同一配置和同一判定语义。
5. 计划的告警、降级状态和阻断原因可以持久化并在页面读取。
6. 提供默认 dry-run 的污染数据审计与恢复工具，不破坏历史计划可追溯性。
7. 页面只展示后端真正生效的参数，避免“修改成功但运行未采用”。

### 2.2 非目标

- 不修改评分、止损、仓位、入场或退出公式。
- 不放宽数据质量门禁以制造可执行计划。
- 不直接修改线上数据库或自动部署服务器。
- 不在本期建设 Hermes 任务中心、管理员认证或任务操作页面。
- 不在本期实现中长线因子、周评分或月度调仓。
- 不整分支合并旧的 `codex/trading-runtime-deployment-repair`；仅逐项参考其中已验证设计。

## 3. 总体架构

第一期沿用 FastAPI、Vue 3、SQLite 和现有 `backend/trading` 边界，不重写交易模块。

### 3.1 前端计划读取

计划列表模型拆分为 `PlanRunSummary`，详情模型保留为 `PlanRunDetail`。总览先读取列表并选择最新有效摘要，再通过详情接口读取 `items`。列表失败、详情失败、计划为空和账户为空分别展示独立状态。

模板不得直接假设 `items` 存在。组件级错误必须变成可见错误信息，不能让整个子页空白。

### 3.2 Scheduler Runner

把“判断应执行什么”和“无限循环等待”分离：

- `SchedulerRunner.tick(now)` 负责计算并执行已到点、当日尚未成功的任务；
- `main_loop` 只负责上海时区时钟、进程信号和轮询节拍；
- `trade_jobs` 记录任务请求、状态、尝试次数、结果和错误；
- `trade_job_locks` 提供跨进程互斥、租约和过期接管；
- 同一任务的幂等键由任务类型、交易日和输入版本组成。

晚启动时，Runner 按时间表顺序补跑已经到点的任务。已经成功的任务不重复执行；失败任务最多重试 3 次。无账户、无激活策略或无股池必须写入明确的 `SKIPPED` 或 `BLOCKED` 结果，不能伪装成完整成功。

### 3.3 Instrument Resolver

代码归一化不得使用 `0009xx` 这种宽泛前缀推断指数。解析规则如下：

1. 已显式带 `.SH/.SZ` 或 `SH/SZ` 前缀时保留市场信息，但仍执行格式校验；
2. 裸股票代码按 A 股市场规则解析：`0/3` 开头为 `.SZ`，`6` 开头为 `.SH`；
3. 只有配置或代码中的明确指数白名单可以覆盖裸代码规则，例如 `000300.SH`、`000905.SH`；
4. Provider、股票池导入和热榜同步统一调用同一个解析器；
5. 无法确定类型时拒绝写入并记录结构化数据问题。

股票代码和指数代码共享六位数字时，调用方必须传递 instrument kind 或使用显式后缀，不允许依赖模糊推断。

### 3.4 数据健康与计划门禁

数据健康接口和计划服务统一读取 `settings.trading_benchmark_codes`，调用同一个 `MarketDataService.check_data_health`。

- 任一配置基准缺失：`BLOCKED`；
- 股池缺失比例 `<= 5%`：`PARTIAL`；
- 股池缺失比例 `> 5%`：`BLOCKED`；
- 持仓行情缺失：`BLOCKED`；
- Provider 返回空数据不得当作成功更新。

计划创建时锁定健康报告摘要、基准集合、股池版本和数据快照哈希。健康报告与计划的判定结果必须可相互解释。

### 3.5 告警与降级持久化

计划从 `GENERATING` 进入终态时，必须在同一状态更新中写入：

- `warnings_json`；
- `degraded`；
- `market_regime`；
- `market_score`；
- `recommended_exposure`；
- `error_json`（失败或阻断时）。

详情接口只返回数据库中的真实持久化值，不从账户快照猜测降级状态。

### 3.6 参数真实性

本期不改变策略公式。前端参数按真实归属分组：

- 策略版本可编辑：后端计划和回测都真实读取的参数；
- 账户风险可编辑：从账户接口维护的仓位、集中度、回撤和持仓数量限制；
- 固定规则只读：仍为代码常量的止损距离等参数，标明当前不可在策略版本中修改。

不得继续提交后端不读取的可编辑字段。

## 4. 每日任务数据流

交易日任务按以下顺序执行：

1. **20:10 `sync_pool_from_hotlist`**：读取最新已收盘交易日热榜，幂等生成股池版本。
2. **20:15 `update_market_data`**：更新最新股池、持仓和全部配置基准的行情。
3. **行情后数据健康检查**：落库数据问题和健康摘要。
4. **20:20 `reconcile_orders`**：恢复 T+1 可卖数量，更新未触发计划状态。
5. **20:25 `generate_daily_plan`**：仅在数据健康为 `OK/PARTIAL` 时生成计划；`BLOCKED` 停止。
6. **23:30 `backup_database`**：执行 SQLite online backup、完整性检查和保留期清理。

非交易日不执行股池同步、行情、复核和计划，但数据库备份仍按计划执行。

## 5. 失败处理

### 5.1 Provider 失败

主 Provider 超时、协议错误或空结果时尝试备用 Provider。所有 Provider 最终失败时：

- 任务进入 `FAILED`；
- 写入稳定错误码和可审计详情；
- 数据健康保持 `BLOCKED`；
- 不生成新计划；
- 不复用旧行情伪装为最新数据。

### 5.2 Scheduler 失败

失败任务最多尝试 3 次。每次尝试都更新持久化计数。进程重启后可以重新认领未完成或租约过期任务，但不能重复执行已经成功的任务。

### 5.3 页面失败

前端分别处理账户、计划列表、计划详情、净值和数据健康请求。局部请求失败时保留其他可用信息，并显示错误来源、重试操作和数据时间。

### 5.4 错误代码与污染数据

污染恢复遵循以下顺序：

1. 默认 dry-run 扫描疑似“股票名称 + 指数行情”错配；
2. 输出受影响股池版本、计划、行情行数和建议动作；
3. 修复前创建数据库备份并执行完整性检查；
4. 创建正确的新股池版本；
5. 回补正确代码行情；
6. 将错误版本记录为不可用于新计划的数据问题；
7. 保留历史计划、旧股池和旧行情用于审计，不原地重写历史输入。

线上修复必须是单独的部署步骤，需在用户明确授权后执行。

## 6. 测试设计

### 6.1 后端

- `normalize_stock_code("000936") == "000936.SZ"`；
- 显式指数 `000905.SH` 保持不变；
- 模糊裸代码在股票和指数上下文中按明确 kind 解析；
- 20:16 启动 Runner 补跑 20:10 和 20:15；
- 重复 tick 不重复创建成功任务；
- 两个 Runner 同时认领时只有一个成功；
- 租约过期后可接管，未过期不可接管；
- 非交易日仅执行备份；
- Provider 空结果进入失败而不是成功 0 条；
- 数据健康和计划门禁使用同一基准集合；
- `warnings/degraded` 生成后可从详情接口读回；
- 污染审计 dry-run 不修改数据库；
- 修复应用前没有备份则拒绝执行。

### 6.2 前端

- 计划摘要类型不包含 `items`；
- 总览先加载摘要再加载详情；
- 有计划、无计划、列表失败和详情失败均有明确渲染结果；
- 详情缺少可选字段时不会抛渲染异常；
- 策略设置不再提供后端未消费参数的可编辑输入。

### 6.3 集成与验收

- 后端全量 pytest；
- 前端新增回归测试并运行完整测试；
- 前端生产构建；
- 空数据库迁移和健康检查；
- Scheduler 晚启动、重启、双实例和三次失败测试；
- 本地浏览器验证 `/preview` 的总览和计划详情；
- Docker Compose Web + Scheduler 冒烟；
- 污染审计 dry-run 报告人工复核。

## 7. 验收标准

1. 总览不再因计划列表缺少 `items` 而空白。
2. Scheduler 到点执行、晚启动补跑、重启恢复且跨进程不重复。
3. `000936` 作为股票解析为 `000936.SZ`，指数必须显式解析。
4. 页面数据健康与计划门禁对同一天给出一致结论。
5. `warnings/degraded` 可以从持久化计划详情读取。
6. 错误股池版本不会再用于新计划，历史记录仍可追溯。
7. 页面不存在“可编辑但后端不生效”的策略参数。
8. 所有约定测试、构建、迁移、Docker 和浏览器验收均有新鲜证据。
